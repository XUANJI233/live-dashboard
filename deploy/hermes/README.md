# Hermes controller integration

These assets make Hermes the conversational controller while Live Dashboard remains the data and device-control service.

- `SOUL.md`: routes relationship and supervision work into the canonical persona skill without duplicating it.
- `skills/strict-study-girlfriend/`: canonical relationship, initiative, teaching strategy, and user-facing voice. Its preloaded `references/method-selection.md` chooses methods and evidence checks by situation; fictional teaching examples never become tasks or shared history.
- `skills/live-mentor/`: Live observation, trust, deduplication, mode, and device-authorization adapter.
- `prompts/supervision.md`: event-triggered review; normal/duplicate/low-confidence cases stay silent.
- `prompts/companion.md`: rate-limited proactive opportunity where speaking is the default when grounded context exists.
- `proactive_candidate.py`: persistent 30-minute probability gate; unchanged output suppresses the agent entirely, and the deep night (01:00-07:00 UTC+08:00) without phone use never selects.
- `followup_candidate.py`: reawakens Hermes after 5, 15, and 30 minutes, then hourly until a later user reply (12-hour stale-root bound); screen-off starts at 15 minutes, and confirmed sleep or the deep night without phone use suppresses the model before invocation.
- `usage_summary.py`: read-only UTC+08:00 per-job cron token accounting from `usage_audit.jsonl`; it observes usage and never enforces a budget.
- `get_controller_context`: returns equivalent compact JSON text and structured views capped at 24 KB. Compatible clients always see the complete bounded object; the Hermes adapter removes the duplicate before model context, keeping its result below the 50K-character spillover threshold without imposing a model-token budget.
- `hermes-gateway-strict-skills.conf`: forces the complete strict persona stack into every Weixin DM session instead of relying on implicit skill selection.
- `trigger_live_supervision.py`: authenticated webhook router for supervision, Live AI work requests, and ledger due wakes. It validates the event (the contract fixture `tests/fixtures/controller_events.json` is shared with Live's outbox), fsyncs it into `live_event_queue.py`'s spool with its mode and any mode-specific task, and only then returns the durable ACK; a Live retry of a queued or handled event is acknowledged again without a second record.
- `live_state_gate.py`: deterministic rest-state read for the candidate scripts. It calls the Live MCP tool `live_dashboard.get_rest_state` on the local listener (`LIVE_DASHBOARD_MCP_URL`, default `http://127.0.0.1:3031/api/mcp`) with `LIVE_DASHBOARD_MCP_TOKEN`, `MCP_SERVER_TOKEN`, or the `MCP_LIVE_DASHBOARD_API_KEY` Hermes already holds for its Live MCP server (the cron script sandbox passes it through); any failure reads as `unknown`, which never suppresses contact.
- `live_event_candidate.py`: one-minute gate for the `live-supervision-review` consumer. It retires expired and superseded spool records (only the newest review or offline event per device survives, and pending ledger due wakes collapse into one; AI work is a durable queue item), dispatches at most one event per run with AI work first and ledger due wakes next, and keeps it in `inflight/` until the next tick: a finished run settles it into `done/`, a failed one sends it back to `pending/` at most twice. A superseded review hands its reason codes to the one that replaces it.
- `dialogue_tail.py` / `weixin_session.py`: bounded, read-only tail of the Weixin conversation (his messages, her replies, and mirrored `[Cron delivery: …]` messages) that every waking gate attaches as `recent_dialogue`; `dialogue_context.py` attaches the same tail to the daily and weekly summaries.
- `configure_isolated_lanes.py`: turns the controller jobs into isolated, mirrored runs pinned to an explicit provider and model (see below), and creates the fallback job; other jobs are left alone. It checks every job and prompt before changing any. A paused event consumer stays paused, with the fallback job paused alongside it, unless `HERMES_LIVE_RESUME_CONSUMER=true`.
- `weixin_delivery_fallback.py`: two-minute no-agent job. iLink rejects many proactive sends (`business_rejected ... prepare failed`); for a settled, sendable response of an `attach_to_session` job that has no `[Cron delivery: …]` mirror (Hermes mirrors only accepted deliveries), it sends the same text to the Android phone as a Live `say` notification, once. Silence follows Hermes's own `is_autonomous_silence_response`.
- `live_mcp.py`: the one authenticated `tools/call` client the scripts share; `cron_outputs.py`: reads a cron run's saved response.
- `configure_live_webhook_ack.py`: enables `script_ack_required` on the existing Live subscription so script failure returns a retryable HTTP error and success returns a matching durable ACK.

Production secrets and job IDs are not stored here. Deploy the scripts under the Hermes profile `scripts/` directory, keep configuration files mode `0600`, bind the Hermes webhook only to the Docker bridge, and use an independent random HMAC secret. The `live-supervision-review` job is the one durable consumer for Live events and on-demand Live AI requests, while daily/weekly scheduled jobs keep their own schedules.

Set `HERMES_CONTROLLER_ENABLED=true` in both the Live container environment and the Hermes profile environment. In this mode, attach both `live-mentor` and `strict-study-girlfriend` to the supervision, companion, memory, daily-summary, and weekly-summary jobs. The former controls facts and authority; the latter controls relationship and output. To use Live AI fallback, explicitly set the flag to `false`, pause those Hermes jobs, and restart Live; never switch automatically from a health probe because that can create two active controllers.

Before enabling unattended jobs, obtain the user's explicit consent, save `supervision_enabled=true`, initialize the Live controller persona with `enabled=true`, and verify current supervision sub-settings. The master supervision switch is the proactive-contact and device-action grant; enabled subsettings narrow vibration and LSP freeze. Live enforces these switches on `send_device_commands` for every controller (dropped actions come back as `supervision_disabled`, `freeze_disabled_by_user` or `vibrate_disabled_by_user`); unfreeze, say and screenshots are never gated. Persona `enabled` controls whether strict voice is active, not consent by itself. In-study pleas, refusal, “别凶了”, or “暂停角色” do not set persona `enabled=false`, soften the persona, cancel commitments, or stop follow-ups. Lasting rule changes use the agreed non-execution review window. If an actual administrative setting has already disabled the persona, Live stops waking Hermes for reviews, device requests and offline events (hard limits already on the phone stay in force), and unattended prompts still check the saved gate; the persona never re-enables itself.

## Isolated lanes

The Weixin conversation is the dialogue lane: it carries only his messages, her replies, and what scheduled work actually sent. Everything automated runs as its own short session. To deploy:

1. Copy the scripts, skills, and prompts (`prompts/` to `$HERMES_HOME/prompts/live`).
2. In `config.yaml`, set `session_events.enabled: false` and keep `session_events.session_key`; it names his conversation for `recent_dialogue`.
3. Stop the gateway, run `configure_isolated_lanes.py` as the Hermes user (with `HERMES_LIVE_RESUME_CONSUMER=true` to start the event consumer), then start the gateway.

`live-memory-sync` no longer needs a cursor file in `$HERMES_HOME/state`, which an isolated run cannot write: Live keeps its feed position. Each run calls `live_dashboard.get_controller_memory_feed` with `{"consumer_id":"hermes-memory","advance":true,"limit":100}` until `has_more` is false (the very first call may add `since` with the cutover time); see `docs/API_PROTOCOL_CONTRACTS.md`. The prompt and skill reference use this server-side consumer protocol: a read advances immediately, and failed processing replays from the returned batch's original `consumer.previous_cursor` (retain the batch or original cutover start when it is null). Filters stay fixed and replayed events are deduplicated. This documentation migration keeps the job paused; it does not change schedules or resume it.

Each controller job then loads both skills with their preloaded references once per run, gets `memory`, `session_search`, `skills`, and `vision` plus the Live MCP server, and mirrors its delivery into the conversation as a `[Cron delivery: …]` message (`attach_to_session: true`). A job-level `model` and `reasoning_effort` now take effect, so the dialogue lane can use a stronger default model without every automated wake replaying the conversation on it. Every isolated job must be pinned: Hermes skips (`[drift_skip]`) an unpinned run whose creation-time model differs from the global default. The configure script pins the global default unless `HERMES_LIVE_JOB_PROVIDER` / `HERMES_LIVE_JOB_MODEL` name another; jobs created elsewhere need `hermes cron edit <id> --provider <p> --model <m>`.

## Token budget

Every Hermes wake is a full agent turn, so cost grows with how often Live wakes Hermes and with what each wake carries. Fixed payload measured on 2026-10-25:

- `live_dashboard` MCP tool schemas: 37 tools, sent with every model call. Live's own `tools/list` JSON measured about 43 KB for 36 tools on 2026-10-30, before the supervision ledger (`ledger_open`, `ledger_update`, `ledger_search`, about 7 KB, replacing `list_commitments`) and `get_activity_history` (replacing both timeline tools) were merged; measure again with `hermes prompt-size`. The 2026-10-25 figure of about 33 KB is not comparable with this count.
- `strict-study-girlfriend`: `SKILL.md` about 15 KB; `references/voice.md` (about 13 KB), `references/conditioning-and-verification.md` (about 31 KB), and `references/method-selection.md` (about 10 KB) are preloaded. `references/device-and-policy.md` stays on demand. Hermes silently skips a preloaded reference over 32 KiB or past 64 KiB in total; `tests/test_skill_preload_budget.py` guards those limits.
- `live-mentor`: `SKILL.md` with `REFERENCE.md` (about 8 KB) explicitly preloaded; reuse the complete reference already in context.
- `get_controller_context`: up to 24 KB per call.

The prompts check deterministic gates before loading strict references and treat skills and references as conversation-scoped: a file whose full text is already in the session is reused instead of loaded again for every event. Every user-facing reply or device action still loads the references its mode requires. Live merges repeated rule-matched reports into one review per device per 10 minutes, and does not wake Hermes for a due periodic review whose usage digest is materially unchanged since the last delivered one (at most two skips in a row, never once that review is four hours old); explicit device requests are never merged or skipped. Supervision, companion, and follow-up contexts carry a whole-window `usage_digest` and only the newest timeline segments, plus a `usage_today` running total for the local day, so older detail is one `get_activity_history` call away instead of riding along on every wake. `get_activity_history` also answers the user's own history questions (minutes per app, last open, sessions by title) with server-side totals.

The Weixin DM session replays its history on every message. Upstream Hermes compacts only at `compression.threshold` of the model context window (50% by default, at least 75% for windows under 512K), so on a large-window model one wake can replay hundreds of thousands of tokens. Cap long-lived sessions in the Hermes profile `config.yaml` and tune the value from measurements:

```yaml
compression:
  threshold_tokens: 100000
  idle_compact_after_seconds: 1800
```

`idle_compact_after_seconds` trades one summary call for smaller replays across the steps of a wake that arrives after 30 idle minutes; keep it only if totals drop. Measure before and after with `hermes insights --days 7` (tokens by source), `hermes prompt-size` (system prompt, skills index, and tool schemas), and `usage_summary.py` (cron jobs, including `silent_calls`, which is spend that ended in `[SILENT]`).
